# 数据语义修复后的产品方向与理解

> 版本：本地集成分支 `codex/remediate-data-semantics-20260904`  
> 判断对象：当前产品，而不是通用研究状态机

## 一句话定位

当前产品应定位为：

> **一个证据边界清晰、可每日更新、由人决定结论晋升的光模块领域研究工作台。**

它不是自动得出行业结论的 Agent，也不是研究过程控制平面。机器负责采集、校验、确定性派生和页面生成；人负责判断语义蕴含、处理冲突，并授权候选进入 canonical。

## 当前产品的四个组成部分

### 1. 领域解释与九页 reader

九页前端把光模块的功能、组件、接口、制造、技术路线、案例、公司位置和研究边界组织成可读主线。它是读者入口，不是事实源。页面必须从 canonical 和受控 section 生成，并显式展示 Fact / Derived / Candidate / UNKNOWN。

### 2. 国内 A 股证据与能力账本

国内线以公开披露为主要证据，使用 points、edges、shipments、route BOM 等账本回答“公司在哪个结构位置有何种已披露能力”。当前能做的是有边界的能力定位；不能把同格重合直接提升为具名产品供货、完整路线能力或市场地位。

### 3. 海外 calls、官网披露与事件情报

海外线同时保留季度来源/claims 与事件 disclosure/evidence 两类职责：前者服务逐条陈述阅读，后者服务事件状态、来源独立性和时间线。当前 reader 已显示季度槽、可用来源、claim、reviewed claim、reviewed event 五级覆盖，并把 asserted 与 corroborated 分开。

### 4. 人工策划的问题模块

问题模块用于把数据缺口转成研究线索和人工研究队列。`depends_on[]` 可以表达真实依赖，但已有材料、页面引用或测试通过都不等于问题完成。问题是否回答及结论是否晋升，只能由人工复核与用户授权决定。

## 数据每日更新与前端生成应如何衔接

建议保持一个简单的日循环：

```text
国内/海外发现任务
→ candidate / staging（不自动晋升）
→ 机器校验、去重、证据锚检查
→ 人工复核与用户授权
→ canonical 更新
→ calls/out 与九页前端确定性重建
→ 发布前机器门与 reader 抽查
```

关键点不是“每天自动改 canonical”，而是“每天恢复发现与候选更新能力”。若当天没有完成复核，页面应继续显示上一次已授权 canonical，并把新发现留在候选/队列中。

本轮已经恢复前端的可生成性：`calls/out` 由 calls renderer 重建，九页由站点构建器重建；静态章节不再固化会随日更变化的公司数、来源行数、槽位数或单位数。

## 当前能回答什么

- 光模块的基本物理功能、主要组件与接口如何连接。
- 某技术路线面对哪些工程约束，以及优势与代价在什么条件下可能反转。
- 某家公司在哪些能力格有公开披露支持、处于何种披露阶段。
- 海外某条管理层陈述是否已核原文，某个事件是 asserted 还是有独立来源支持的 corroborated。
- 当前数据在哪些位置缺证据、缺统一分母或只能形成候选。

## 当前不能回答什么

- 仅凭能力格重合判断某公司提供某个具名产品或服务完整技术路线。
- 仅凭来源槽位或抓取数量判断研究结论覆盖。
- 把 reviewed 第一方披露当作独立证实，或把订单/计划当作已出货。
- 把异构出货量跨公司求和、排名或推导市场份额。
- 在没有 exact BOM、product scope、统一边界数据时判定具体产品内部器件、供货关系、全系统净功耗或路线胜负。

## 下一阶段方向

### 优先级 1：完成三个真实垂直切片

继续使用已经收敛的三个入口：

1. 800G DR8 物理组件链；
2. LPO 的功耗来源与责任转移；
3. 800G LPO 具名产品级证据。

每个切片只要求形成读者可见回答、证据锚、反证条件和 UNKNOWN。三个切片会提供真实样本，用来判断现有账本和页面是否足够，而不是先抽象通用流程。

### 优先级 2：恢复日更，但把发现和晋升拆开

- 国内与海外发现任务可以每日运行。
- 自动输出只能进入候选、staging 或日报。
- canonical 晋升维持人工复核与用户授权。
- 每次获准 canonical 变化后统一重建前端，不让 generated output 反向成为事实源。

### 优先级 3：逐项裁决 canonical 数据问题

建议另立小工作包依次处理：

1. points 判定等级中过程备注的可逆搬迁；
2. triage 主键与日期完整性；
3. macro evidence 的原子来源与错误口径；
4. shipments 直接披露与真实推断的分离；
5. edges 产品范围不足。

每个问题单独授权、单独测试、单独回滚。不要一次性重构全部账本。

### 暂不做

- 不 fork 出第二个领域权威仓库。
- 不恢复 closure pilot、自动 close/reopen、receipt、manifest 或 snapshot lineage。
- 不因为 C5 粗粒度带来不便就立即新增 schema；先看两个真实切片是否确实被阻塞。
- 不合并两条海外主张链，除非先明确要替换的读者行为和迁移路径。
- 不删除 archive 或空表，直到依赖审计获得专项授权。

## 架构判断

当前最重要的架构不是更多“控制”，而是三个稳定边界：

1. canonical 是唯一事实源；
2. deterministic reader 只读 canonical 并显式标注推导；
3. daily discovery 只产候选，不取得晋升权。

只要这三个边界保持，国内日更、海外日更、问题模块和九页前端可以继续在同一仓库演进。新架构只有在两个真实切片被现有结构阻塞、真实生产数据已经出现、能替代一个既存人工步骤且对读者结论必需时，才值得进入用户裁决。
