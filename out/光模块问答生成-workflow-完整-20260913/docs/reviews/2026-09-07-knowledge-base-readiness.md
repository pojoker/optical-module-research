# 公司知识库能否在当前仓库独立继续？

2026-09-07 · 本地核验结果

**结论：底账和主要程序已经在，但资料与增量尚未收齐。目前可利用本机旧目录继续工作，还不能算独立迁移完成。** 学习网页能生成，不能替代这项验收。

## 还没有收齐的三件事

**1. 原始资料仍依赖旧目录。**

当前 `corpus/annual`、`corpus/annual-2024` 都是指向旧workflow-rehearsal的软链接，两批合计约1.76 GB、1,942个文件（含文本等，并非全是PDF）。Git忽略这些目录，因此单独克隆当前GitHub仓库不会带回这些资料。

当前还没有 `corpus/ir`。旧主目录留有260个投关资料文件，旧回补工作树另有20个；两组尚未去重，不能直接相加当成独有材料数量。海外sources/disclosures中的local_path目前全部为空，当前主要依靠URL与摘录，不是完整离线原文库。

**2. 9月3日的回补成果尚未全部承接。**

与旧 `workflow-rehearsal-domain-mainline` 当前文件对照，找到：

- 国内：2条新增能力记录（P275/P276），5条既有能力记录的证据更新，1条出货记录（SE106）。
- 海外：4条季度来源记录（NVIDIA、Broadcom、Marvell、Credo），1条事件（EV035）及相应披露、陈述和证据连接记录。
- 原始问答：29份qa.jsonl不同；判定记录和研究问题导航也有差异。

这里确认的是**旧文件存在、当前尚未承接的差异**，没有重新核验这些公司主张，也没有批准将其写入当前底账。采集代码同样有版本差异：当前已有9月5日日更修复，不能用旧回补分支整批覆盖。

**3. “继续研究和更新”的日常入口尚未完整验收。**

新日更模块将资料/候选写入仓库外的daily-state；旧 `corpus/_daily_update.py` 仍保留另一套更新入口。两套入口并存，后续应明确日常用哪套、历史回补用哪套，以及候选如何交给执行者研究再审核。

本轮没有在用户crontab中找到包含项目名称/上述模块名的任务，也没有在用户LaunchAgents配置中找到相应匹配。这只覆盖两个位置，不能据此断言其他调度系统中没有任务。没有修改调度或启动网络采集。

## 本轮验证能证明什么

- `scan.py --check`：通过①—⑭结构检查；程序报告语料最新文件距今22天、宇宙内缺席年报0家。**检查使用了仍指向旧目录的原始年报**，不能证明独立性。
- `python -m calls check`：通过账本结构与引用检查。工具中的reviewed事件措辞只是账本状态，不表示本轮完成了事实复核。
- 文件与入口核对：确认底账、代码、软链接、缺失目录和上述旧分支差异。

没有重建公司报告、运行真实日更或模拟断开旧目录；不把静态检查通过写成端到端运行通过。没有迁移原始资料、修改canonical或合并分支。

## 建议下一步

先做一次**公司知识库承接**：

1. 把原始年报、投关资料放到稳定资料目录，保全、去重并核对链接；可以独立于代码仓库，不必把大批PDF塞进GitHub。
2. 分别审核上述国内、海外、问答回补增量；代码取当前修复与仍需要的回补能力，领域结论逐项核验后另行授权入库。
3. 从指定入口实际完成一次“采集候选 → 委派研究 → 审阅 → 公司报告更新”，验证不依赖待退役的旧目录。

完成这些，才可以说你认可的公司知识库工作流已在这里接住。此前保留旧目录；学习网页继续作为另一套已有方案，不承担知识库承接完成的证明。
